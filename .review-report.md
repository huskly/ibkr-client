# Review report

## Findings

1. **P1 — A multi-month expiry operation still starts work after one month fails** (`src/ibkr/ibkrClient.ts:4216-4220`, `src/ibkr/ibkrClient.ts:4707-4712`)

   `getOptionExpiries` starts as many as eight `discoverOptions` calls in one `Promise.all`, but each call creates its own `AbortController`. A terminal definition failure aborts only the jobs for that month. The other months in the same public operation can continue to enqueue, start, and retry their definition chunks after `getOptionExpiries` has rejected. Thus, a multi-month request can still leave substantial unwanted broker traffic. It can also have as many as eight separate eight-item chunks submitted to the scheduler, contrary to the README statement that the operation submits at most eight definitions at one time. The operation must use one cancellation scope for all months, or it must process months so that a failed month cannot leave sibling work.

2. **P1 — The required repository check fails on the changed scheduler** (`src/ibkr/requestScheduler.ts:185`, `src/ibkr/requestScheduler.ts:416`)

   `npm run lint` reports `@typescript-eslint/prefer-promise-reject-errors` for rejection with `options.signal.reason` and `@typescript-eslint/no-unnecessary-condition` for `if (!job.aborted)`. Therefore, the PR does not pass the required check and CI will fail. `npm test` passes all 263 tests.

3. **P2 — The public abort option stops only discovery, not the full chain operation described in the README** (`src/ibkr/ibkrClient.ts:4251-4254`, `src/ibkr/ibkrClient.ts:4275-4279`, `src/ibkr/ibkrClient.ts:4845-4846`)

   `loadOptionContracts` removes the caller's abort listener as soon as definition discovery finishes. `getOptionChain` and `getOptionChainSnapshot` then start market-data snapshot work without the signal. If the caller aborts after discovery finishes, or while snapshot requests are queued, those methods can continue all snapshot work and resolve successfully. This conflicts with the documented contract that the options value stops one operation and that an aborted operation rejects with the signal reason. Either propagate the signal through the remaining chain work, or narrow the public documentation and API so that it clearly controls definition discovery only.


## Resolution

Commit `e24479673a162126f05d0bc2267e439a46818a29` resolves all findings.

- Multi-month discovery is sequential. A failed month cannot start a later month.
- The repository lint findings are resolved.
- The caller signal controls discovery and both market-data snapshot requests. A signal that aborts in the handoff between discovery and snapshots is safe because each scheduled snapshot checks the signal before it starts. An abort during the snapshot warm-up wait cannot start the second broker request.
- Operations that have a signal bypass the shared discovery cache. Thus, one caller cannot cancel or poison cached work for another caller. Operations without a signal keep the existing memoized discovery behavior.
